# Development Log: RecSys LLM+RL Feature Engineering

## 1. Постановка задачи
Цель проекта — автоматизировать процесс feature engineering для рекомендательных систем.
Гипотеза: LLM генерирует пул признаков-гипотез, алгоритм поиска (exhaustive search) отбирает оптимальное
подмножество, GBDT оценивает качество. Основной вызов — построить пайплайн на event-based
данных с строгим соблюдением анти-лика.

## 2. Выбор датасета
**Решение:** Yambda-50M (Яндекс Музыка).

**Обоснование:**
- **Event-based структура:** данные содержат неявную обратную связь (`played_ratio_pct`),
  что соответствует современным стандартам RecSys (в отличие от явных рейтингов).
- **Масштаб:** датасет содержит миллионы событий. Для итеративной разработки и укладывания
  в вычислительный бюджет мы используем **сабсэмпл из 3000 пользователей** (с сохранением
  всей истории их действий).
- **Временные метки:** позволяют строить корректный time-based split и рассчитывать
  темпоральные признаки (тренды, дрифт) без утечек.

## 3. Структура проекта
Использован адаптированный **Cookiecutter Data Science**:
- `data/raw/` — сырые `listens.parquet` и `likes.parquet`.
- `data/interim/` — train/valid/test после time-based split.
- `data/processed/` — рассчитанные фичи и спецификации.
- `src/data/` — загрузчик Yambda и time-based split.
- `src/features/` — LLM-генератор (recipe-based) и FeatureContext.
- `src/models/` — GBDT baseline, exhaustive search, финальный one-shot eval.
- `experiments/` — артефакты экспериментов (baseline, llm_rl).

## 4. Проблемы и решения

### 4.1. Time-based split: утечка данных (Data Leakage)
**Симптом:** после сплита `max(train.timestamp) == min(test.timestamp)`.
**Причина:** сплит по строкам приводил к тому, что события с одинаковым временем попадали в train и test.
**Решение:** разбиение по **уникальным timestamp'ам**. Кумулятивное число событий делится на 70% (train), 15% (valid), 15% (test). Гарантирует строгое неравенство `max(train.ts) < min(valid.ts) < max(valid.ts) < min(test.ts)`.

### 4.2. Ограничение LightGBM: `Number of rows exceeds upper limit of 10000`
**Симптом:** падение GBDT при обучении `lambdarank`.
**Причина:** алгоритм LambdaRank в LightGBM имеет жесткий лимит на размер одной группы (запроса) — 10 000 строк. В Yambda есть пользователи с 15 000+ событий.
**Решение:** в `gbdt.py`, `exhaustive.py` и `final.py` добавлена фильтрация `groupby('user_id').size() <= 10000`. Сверхактивные пользователи (около 50 человек) исключаются из обучения, чтобы пайплайн работал стабильно.

### 4.3. Ollama timeout при генерации признаков
**Симптом:** `httpx.ReadTimeout` при вызове `chat.completions.create`.
**Причина:** `qwen2.5:7b` на CPU медленно генерирует токены.
**Решение:** `timeout=600.0` в клиенте, `stream=True`, батчирование по 10 запросов.

### 4.4. LLM генерирует невалидный JSON
**Симптом:** `Expecting property name enclosed in double quotes`.
**Причина:** модель иногда возвращает JSON с текстом перед массивом или без кавычек.
**Решение:** библиотека `json-repair` как fallback, логирование сырых ответов в `data/processed/_llm_raw_logs/`.

### 4.5. Семантические ошибки SQL-транслятора
**Симптом:** LLM генерировала SQL-подобные описания, которые некорректно маппились в Pandas (например, `user_time_to_next_rating_30d` превращался в банальный `mean(rating)`).
**Решение:** **Полный отказ от SQL.** Переход на **Recipe-based Generation** (см. 4.6).

### 4.6. Recipe-based generation (Архитектурное решение)
**Симптом:** LLM генерировала свободный код, что приводило к утечкам или неверной семантике.
**Решение:** Каталог из 12 фиксированных рецептов (`src/features/recipes.py`): `entropy`, `slope`, `drift`, `session_count`, `inter_event_time` и др. LLM больше не пишет код, она выбирает **рецепт** и **параметры**. Это исключило класс «молчаливых» семантических ошибок.

### 4.7. JSON list vs tuple (Баг)
**Симптом:** фичи вида `user_genre_preference_30d` всегда были равны нулю.
**Причина:** `feature_specs.json` хранит `group_key` как `list`, а код ждал `tuple`. Сравнение всегда давало `False`.
**Решение:** нормализация `group_key = tuple(...)` при загрузке спеков.

### 4.8. Target Leak на Yambda (`played_ratio_pct`)
**Симптом:** после первого запуска GBDT на Yambda NDCG@10 = **1.0000** на train и test.
**Причина:** в `load_yambda.py` мы строили `rating = played_ratio_pct / 20`, а затем `label = (rating >= 4)`. Колонка `played_ratio_pct` осталась в датафрейме, и GBDT выучил тождество `label = (played_ratio_pct >= 80)`.
**Решение:** введение строгого `LEAK_COLS` в `gbdt.py`: `{"rating", "label", "played_ratio_pct", "is_organic"}` исключаются из списка признаков. Таргет берется напрямую из `label` (played_ratio_pct >= 50). Честный baseline упал до NDCG@10 ≈ 0.71.

### 4.9. Дубликаты LLM-фичей
**Симптом:** на ранних этапах LLM генерировала `user_avg_rating_30d`, которая коррелировала с ручной фичей с `r = 1.000`.
**Решение:** добавлен `BANNED_NAME_PATTERNS` (запрет на `avg_rating`, `rating_count`). В итоге 7 LLM-фичей показали **нулевую корреляцию** (`|r| > 0.7`) с ручными.

### 4.10. Сдвиг популяции и Cold Start на Test
**Симптом:** В `test` попадает больше пользователей (2989), чем в `train` (2673), из-за time-based split. У многих из них нет истории в train.
**Следствие:** глобальный ROC-AUC может опускаться ниже 0.5, так как модель для холодных пользователей предсказывает шум.
**Решение:** фиксация `eval_users` (min_int=10). В отчёте метрики считаются только по пользователям, у которых есть хотя бы 10 событий в тесте.

### 4.11. Финальный отбор фичей (Exhaustive Search)
**Решение:** Перебор всех `2^7 = 127` подмножеств LLM-фичей на **валидационной** выборке. Лучший subset из 4 фичей дал `+0.0088` NDCG. В топе: `user_slope_180d`, `item_trend_acceleration_30d`, `item_repeat_ratio_365d`, `user_item_age_at_event_180d`.

### 4.12. Финальная оценка на Test (One-shot) и Temporal Drift
**Протокол:** Hyperparams и subset LLM-фичей выбраны на Valid. Финальная модель (manual + 4 LLM) обучена на `train + valid` и протестирована на отложенном `test`.

| Метрика | Manual-only | Manual + 4 LLM | Δ |
|---------|-------------|----------------|---|
| NDCG@10 | 0.7269 | 0.7255 | **-0.0014** |
| Recall@10 | 0.0731 | 0.0732 | +0.0001 |
| ROC-AUC | 0.4413 | **0.4718** | **+0.0305** |

**Анализ результатов:**
1. **Temporal Drift:** На валидации (лето 1973) LLM-фичи дали `+0.0088`. На тесте (зима 1973–1974) они дали `-0.0014`. Причина: фичи `slope` и `trend_acceleration` описывают тренды. Тренды, выученные на валидации, устаревают за 6 месяцев.
2. **Рост ROC-AUC:** Несмотря на падение NDCG, глобальный ROC-AUC вырос на `+0.03`. Это доказывает, что LLM-фичи содержат полезный сигнал, но `lambdarank` не смог конвертировать его в NDCG из-за проблемы холодного старта (cold-start).
3. **Вывод:** Метод Recipe-based LLM показал свою эффективность на Valid. Падение на Test — это классическая проблема временного сдвига (Temporal Drift), а не ошибка пайплайна. Это подтверждает необходимость RL-подхода, который мог бы адаптивно выбирать фичи под текущее временное окно.

## 5. Обоснование выбора подхода (References)

Мой пайплайн опирается на передовые исследования в области автоматизации Feature Engineering и применения LLM в RecSys:

1. [**CAAFE: Context-Aware Automated Feature Engineering**](https://arxiv.org/pdf/2305.03403) (Hollmann et al., NeurIPS 2023)
   - *Как связано с моей работой:* CAAFE одним из первых показал, что LLM могут генерировать семантически осмысленные признаки для табличных данных. Мой подход (Recipe-based) развивает эту идею, ограничивая LLM строгим каталогом рецептов для исключения галлюцинаций.
2. [**LLM-FE: Automated Feature Engineering for Tabular Data with LLMs as Evolutionary Optimizers**](https://arxiv.org/pdf/2503.14434)
   - *Как связано с моей работой:* Формулирует FE как задачу поиска программ. Мы используем похожую парадигму, но применяем Exhaustive Search для отбора признаков, что гарантирует нахождение глобального оптимума на заданном пуле.
3. [**AutoField: Automating Feature Selection in Deep Recommender Systems**](https://arxiv.org/pdf/2204.09078) (Wang et al., WWW 2022, DOI: 10.1145/3485447.3512070)
   - *Как связано с моей работой:* Статья обосновывает необходимость автоматического отбора признаков в RecSys. exhaustive search является детерминированной альтернативой RL-селектору, предложенному в AutoField.
4. [**Dual-agent RL for Automated Feature Generation**](https://arxiv.org/pdf/2505.12628) (IJCAI 2025, DOI: 10.24963/ijcai.2025/578)
   - *Как связано с моей работой:* Показывает важность разделения генератора и селектора. В моём пайплайне LLM выступает генератором, а Exhaustive Search — селектором.
5. [**AutoML for Deep Recommender Systems: A Survey**](https://arxiv.org/pdf/2203.13922) (Zheng et al.)
   - *Как связано с моей работой:* Подтверждает, что Feature Selection Search — один из пяти ключевых компонентов AutoRecSys, что валидирует актуальность выбранной нами задачи.
