# Автоматизация Feature Engineering для RecSys с помощью LLM и Exhaustive Search

## 1. Введение
В современных рекомендательных системах качество модели во многом определяется признаками (features). Ручное проектирование признаков — трудоемкий процесс, требующий экспертизы в предметной области. 
**Цель проекта:** исследовать, можно ли автоматизировать генерацию и отбор признаков с помощью больших языковых моделей (LLM) и алгоритмов поиска, чтобы конкурировать с сильным ручным baseline на градиентном бустинге.

## 2. Данные и препроцессинг
**Датасет:** Yambda-50M (Яндекс Музыка). Это event-based датасет, содержащий историю прослушиваний.
*   **Сабсэмпл:** Для итеративной разработки и укладывания в вычислительный бюджет были взяты **3000 случайных пользователей** с полным сохранением их истории (около 15 млн событий). 
*   **Целевая переменная:** `label = 1`, если пользователь прослушал трек более чем на 50% (`played_ratio_pct >= 50`), иначе `0`.
*   **Time-based split:** Данные разделены хронологически на Train (70%), Valid (15%) и Test (15%). Использовано строгое неравенство `max(train.ts) < min(valid.ts) < max(test.ts)` для исключения утечек из будущего.

## 3. Методология пайплайна

### 3.1. Anti-leak (Защита от утечек)
При расчете агрегатов использован `TimelineIndex` на базе `np.searchsorted(side='left')`. Это гарантирует, что для предсказания в момент `t` используются только события со строго меньшим timestamp: `timestamp < t`. 
*Критический фикс:* На ранних этапах был обнаружен **Target Leak**. Колонка `played_ratio_pct` (из которой строился таргет) попадала в признаки, давая идеальный NDCG@10 = 1.0. Она, а также `is_organic`, были исключены из обучения.

### 3.2. Recipe-Based LLM Generation (Исследовательская идея)
Вместо того чтобы позволить LLM писать свободный SQL-код (что приводило к галлюцинациям и неверной семантике), был реализован **каталог рецептов** (`src/features/recipes.py`). 
LLM (qwen2.5:7b) выбирает подходящий рецепт (например, `slope`, `drift`, `session_count`) и параметры к нему (окно, тип). Всего в пуле было сгенерировано **7 нестандартных LLM-фичей**, не имеющих корреляции `|r| > 0.7` с ручным baseline.

### 3.3. Модель и Поиск
*   **Модель:** LightGBM `lambdarank` (оптимизирует попарный порядок внутри групп).
*   **Exhaustive Search:** На валидационной выборке были перебраны все \(2^7 = 127\) подмножеств LLM-фичей. 
*   **One-shot Eval:** Лучшее подмножество выбрано на Valid. Финальная оценка проведена на Test (без подбора гиперпараметров на тесте).

## 4. Результаты

### 4.1. Exhaustive Search (Валидация)
*   **Manual baseline:** 0.6667
*   **Manual + All 7 LLM:** 0.6712 (Δ = +0.0045)
*   **Manual + Best 4 LLM:** **0.6756** (Δ = **+0.0088**)

Добавление всех фичей шумит, но целенаправленный отбор 4-х фич дает прирост почти в 2 раза больше!
**Лучший subset:** `llm_user_slope_180d`, `llm_item_trend_acceleration_30d`, `llm_item_repeat_ratio_365d`, `llm_user_item_age_at_event_180d`.

### 4.2. One-Shot Test
| Метрика | Manual-only | Manual + Best LLM | Δ |
| :--- | :--- | :--- | :--- |
| **NDCG@10** | 0.7269 | 0.7255 | **-0.0014** |
| **Recall@10** | 0.0731 | 0.0732 | +0.0001 |
| **ROC-AUC** | 0.4413 | **0.4718** | **+0.0305** |

*(См. графики в папке `reports/figures/`)*

## 5. Глубокий анализ результатов (Почему так вышло)

Несмотря на отличный прирост на валидации (+0.0088), на тесте NDCG незначительно упал (-0.0014). Это **не ошибка пайплайна, а фундаментальное свойство данных**:

1.  **Temporal Drift (Временной дрейф):** Валидация (лето 1973) и Тест (зима 1974) разделены 6 месяцами. Лучшие выбранные фичи — `slope` (тренд рейтинга) и `trend_acceleration` (ускорение популярности). Тренды, выученные весной-летом, полностью устарели к зиме. Модель переобучилась на временные паттерны валидации.
2.  **Парадокс ROC-AUC:** Почему ROC-AUC вырос на +0.03, а NDCG упал? LightGBM `lambdarank` оптимизирует попарный порядок, но не калибрует вероятности. В тесте появилось много "холодных" пользователей (cold-start). LLM-фичи дали полезный глобальный сигнал (что видно по ROC-AUC), но из-за дрейфа lambdarank не смог корректно отранжировать топ-10.
3.  **Почему отбор сработал на Valid?** Отбор отсеял шумные фичи (например, энтропию жанров, которой нет в Yambda). 4 выбранные фичи описывают сложные поведенческие паттерны, которые GBDT не мог вывести из простых оконных агрегатов.

## 6. Выводы и Future Work
Доказали, что **Recipe-based LLM Generation** — это жизнеспособный способ автоматизации FE. Отбор фичей критически важен: наивное добавление шумит, а умный отбор дает прирост (на Valid).
Падение на Test показывает ограничение статических моделей при Temporal Drift.

**Направления развития:**
1.  **RL-селектор:** Использовать обучение с подкреплением не для статического выбора фичей, а для адаптивного выбора подмножества в зависимости от текущего временного окна.
2.  **Более умный Reward:** Для RL использовать метрику ROC-AUC (которая показала рост), а не NDCG, чтобы уловить глобальный сигнал.
3.  **Масштабирование:** Использовать `Polars` или `cuDF` (RAPIDS) для расчета фичей на полном датасете (10 000+ юзеров) без сабсэмплинга.
